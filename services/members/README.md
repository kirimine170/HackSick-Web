# HackSick 会員管理

Cloudflare WorkersとD1上で動く，Better Authを使った会員ポータルの初版です．Google Workspaceログイン，メールの確認コード，会員情報の初回紐付け，運営による資格・支払確認済み期間の登録，Square契約IDの紐付け，変更履歴に対応します．

会員ポータルは `https://members.hacksick.com/`．HSAPの確認済み3名と，Squareの実際の月額会員1名を本番D1へ取り込み済み．本番Googleログインと10％の資格判定を確認した．一般ショップは `https://shop.hacksick.com/`．Square Onlineは無料プランのまま，切替前に受け付けた注文の処理に使う．

既存のSquare商品バリエーションを参照するWeb Payments SDKのカード決済を実装し，本番の購入受付を有効にした．在庫は一般ストア・POSと共通で，会員用在庫の分割・振替はしない．Sandboxで単品・5袋セットの決済，在庫減算，再試行の重複防止を検証し，Squareから本番Webhookへの模擬通知も200 OKで受信した．運用記録はGit管理外の `ROLLOUT.md` に保管する．

## 独自ショップの切り替え手順

`shop.hacksick.com` の単発購入はゲストでも利用できる．会員価格・限定商品・クーポン・定期便にはメール確認が必要．ゲストの連絡先メールは取引メールに使い，注文履歴は購入したブラウザに紐付ける．ログイン済みの購入者には，同じアカウントの支払済み注文から配送先を補完する．`members.hacksick.com` は会員価格の購入と定期便の申込・運営向け．両サイトは同じWorkerとD1を使用する．Cookieはホスト内のみで使い，SquareのWebhookとOAuthの戻り先は会員ホストに置く．公開済みの珈琲・書籍は同じSquare SKUを使用し，店舗・EC間で在庫を移さない．

1. `wrangler.production.example.jsonc` を `wrangler.production.jsonc` にコピーし，既存Workerと同じD1・Squareアプリ・拠点を設定する．実設定とSecrets，運用記録，注文データはGit管理外．本番DBのバックアップと既存マイグレーション履歴を確認してから未適用のマイグレーションを適用する．
2. HTTPSのSandboxでカード決済，お試しからの定期便，注文通知，発送を確認する．最初の公開はカード決済で行う．Apple PayはSquare公式の検証ファイルを `/.well-known/apple-developer-merchantid-domain-association` で配信し，Square Developer Consoleで対象ホストを登録する．Apple Pay・Google Payを対応端末で検証してから `WALLET_ENABLED=true` にする．
3. `SHOP_BASE_URL=https://shop.hacksick.com` とWorker Route `shop.hacksick.com/*` を設定する．現行のDNSレコードを使用し，切替前は302ルールを有効にしておく．`STOREFRONT_CHECKOUT_ENABLED=false` の間は一般ショップで新しい支払いを受け付けない．
4. 切替前のSquare Online注文を抽出し，受注済みの残件を照合する．Square Online新規受付停止，302解除，`STOREFRONT_CHECKOUT_ENABLED=true`，公式サイトの作品リンクの公開を同じ切替作業で行う．旧店の残件は旧手順で完了させる．障害時は一般ショップの新規受付だけ停止し，302とSquare Online受付を戻す．その間も購入済み注文・定期便は既存IDで処理する．

限定商品は「ショップの注文・発送・在庫 → 限定商品・クーポン・ESSEN担当者」で設定する．Squareで商品とSKU・価格・在庫追跡を準備し，対象ステータスを付けた人だけに販売する．既存の商品とは別のSKUを使う．クーポンは対象商品と会員割引との併用条件を指定する．「割引額が大きい方」は同額なら会員割引を使う．「併用する」は会員割引を引いた後の対象商品代金にクーポンを適用する．決済否承認では利用枠が戻り，結果不明では照合まで残る．返金時に消費済みの利用枠が部門承認なく自動復活することはない．

ESSENは第2段階．同一Square加盟店の別拠点IDを `ESSEN_LOCATION_ID` に設定し，署名済みWebhookと注文IDの照合を検証する．`ESSEN_BASE_URL=https://shipping.byessen.com` を専用ホストに設定し，Cloudflare for SaaSでこのホストだけをWorkerへ接続する．登録済み `@byessen.com` 担当者のメールでログイン・更新ができることを確認してからESSEN用SKUを販売する．発送元の異なるSKUは別会計．売上と支払いはHackSickが扱い，パートナー画面は発送情報だけ返す．

## アカウントと設定の準備

Better Authはnpmパッケージとして自分たちのWorkerで実行するため，Better Auth自体のサービス登録は不要です．既存のCloudflareとResendを利用できます．

2026年11月3日に，Google Cloudのプロジェクト `hacksick-members-auth` とInternalのOAuth同意画面を作成した．アプリ名はHackSick Members，サポート窓口は `hsap@hacksick.com`，Googleからの変更通知先は `shop@hacksick.com`．ローカル用のウェブOAuthクライアント `HackSick Members Local` は，戻り先を `http://localhost:8787/api/auth/callback/google` に限定した．実際のWorkspaceアカウントで，ローカルポータルへのGoogleログインが成功した．

認証情報はGit管理外の `.dev.vars` と `.credentials/` に保存し，ファイル権限を600に設定した．本番OAuthクライアント，専用D1，HSAPと月額会員の取り込み，Square専用OAuthアプリは接続済み．Resendの送信専用キーを接続し，本番メールコードでのログインを確認済み．このログイン確認で，運営権限や会員資格は自動付与していない．

### Google Cloud

1. HackSickのGoogle Workspace組織でプロジェクトを選択または作成する．
2. Google Auth Platformのアプリ情報と同意画面を設定する．GoogleログインはWorkspace向けなので，組織内アプリを選べる場合はInternalにする．月額会員は個人メールの確認コードでログインできる．
3. ウェブアプリケーションのOAuthクライアントを作成する．必要なスコープは `openid`，`email`，`profile`．DriveやWorkspace管理APIの権限は要求しない．
4. 承認済みリダイレクトURIへ次を登録する．

```text
http://localhost:8787/api/auth/callback/google
https://members.hacksick.com/api/auth/callback/google
```

本番は `members.hacksick.com` を使用しています．本番用クライアント `HackSick Members Production` と専用D1を作成済みです．検証用ホストを別に作る際は，そのホストの `/api/auth/callback/google` も登録する．本番と検証はOAuthクライアントとD1を分離する．

クライアントIDとクライアントシークレットは，ローカルでは `.dev.vars`，公開時にはWorkerのSecretsへ設定する．チャット，Git，ブラウザ側コードへ貼り付けない．Google設定の `hd=hacksick.com` は所属確認に用い，会員資格は台帳から登録された資格で判定する．

### メールとCloudflare

| 設定 | 用意するもの |
| --- | --- |
| `BETTER_AUTH_SECRET` | 環境ごとに生成する32バイト以上のランダムな秘密情報 |
| `GOOGLE_CLIENT_ID` | GoogleのウェブOAuthクライアントID |
| `GOOGLE_CLIENT_SECRET` | 同クライアントのシークレット |
| `RESEND_API_KEY` | 認証済み送信ドメインに使えるResendのキー |
| `MAIL_FROM` | 認証済み送信元．`HackSick <noreply@notify.hacksick.com>` を使用 |
| `AUTH_BASE_URL` | ローカルでは `http://localhost:8787`．公開時は実際のHTTPSオリジン |

送信元ドメインのDNS認証を済ませる．既存の認証済みドメインを再利用する場合は `MAIL_FROM` をそのドメインの送信元へ変更する．Google WorkspaceのMXレコードは変更しない．

Cloudflareでは，このサービス専用の検証用D1を用意し，DBバインディングを `DB` にする．本番用D1と検証用D1は分ける．このリポジトリの `wrangler.jsonc` に入っているゼロのdatabase IDはローカル用であり，リモート操作には使わない．

## ローカルで動かす

このディレクトリで実行する．Node.js 22.18以上を使用する．

```bash
npm ci
cp -n .dev.vars.example .dev.vars
chmod 600 .dev.vars
```

`.dev.vars` に値を設定する．`BETTER_AUTH_SECRET` は例えば `openssl rand -base64 32` で生成し，手元で保存する．GoogleとResendの値を用意するまで，ログインの実接続は利用できない．秘密情報をログに出力するメール送信モードは設けていない．

```bash
npm run db:local
npm run dev
```

`http://localhost:8787` を開く．このコマンドはローカルD1だけを使用する．Googleログインまたはメールコードで最初の運営アカウントを作成する．ログインしただけでは運営権限や会員資格は付与されない．

## 最初の運営担当の登録

ローカルD1へ，実際にログインを完了した担当者のuser IDを指定して登録する．user IDはログイン後の `/api/me` に返る．

```sql
INSERT INTO operators (auth_user_id, role, created_at)
SELECT id, 'manager', strftime('%Y-%m-%dT%H:%M:%fZ', 'now')
FROM user
WHERE id = '<本人確認済みのuser ID>' AND emailVerified = 1;
```

ローカルでは `npx wrangler d1 execute DB --local --command '<SQL>'`，公開時は対象環境を確認したうえでD1コンソールから登録する．Workspace全体やメールの末尾を条件に管理権限を付けない．閲覧専任者は `role='viewer'` とする．

## 会員を登録する

1. 運営画面で，表示名，本人確認済みメール，該当者のHSAP IDを登録する．同じ人のHSAPと月額会員には同じ会員レコードを使う．共有メールアドレスを本人確認に使わない．
2. HSAPは承認・在籍・退会を既存台帳で確認し，根拠のHSAP IDと有効期間を登録する．月額会費があるHSAP契約の入金状況は，別途Square契約として管理する．
3. 月額会員はSquareの対象プラン，請求，支払完了と対象期間を確認し，Payment IDと支払済み期間を資格として登録する．初回支払後の単純な「1か月足し」や，`ACTIVE`／`charged_through_date`だけでの入金認定はしない．
4. SquareのCustomer IDとSubscription IDを本人へ紐付ける．契約を登録しただけでは資格は付かない．カード番号や保存カード情報は登録しない．
5. 会員が登録済みメールでログインすると，初回のみ本人へ紐付く．異なるメールや重複アカウントは自動統合せず，運営が両方の所有者を確認して対応する．

資格の有効期間は開始を含み，終了を含まない．画面の日時入力と表示は日本時間，DBはUTCのISO文字列とする．例えば11月分を11月末まで有効にするなら，終了は12月1日0時（日本時間）とする．将来分の入金記録があっても，途中の未払い期間は有効にならない．HSAPと月額の双方に該当しても割引率は10％．取消・利用停止は次の資格照会から反映する．

運営担当の操作は，担当者ID，対象会員，確認根拠・理由，変更日時を履歴に残す．月額会員は許可リストのSquareプランだけを対象に，請求・注文・実際の入金を定期照合する．運営が手動取消した資格は同期で復活させない．自動督促・自動解約・カード更新・Workspace停止は実行しない．

## 会員ショップの決済

- `/api/shop` は同じSquareカタログと店舗在庫を読み取る．単品 `HS-COFFEE-MOCHA-10G`，5袋セット `HS-COFFEE-MOCHA-5PACK` の既存variationを使う．SKUの変更，販売停止，追跡なし，不明な在庫は決済を止める．
- サーバーが税込432円／2,052円から商品代金10％を円単位で計算し，送料500円を加える．割引前の商品代金5,000円以上で送料無料．現行条件は，後述の収益モデル案の4,000円と別である．単品1袋の支払合計889円，5袋1セット2,347円をSquareの計算APIでも確認した．
- カードはSquare Web Payments SDKから直接Squareへ送信し，3Dセキュアの確認を `card.tokenize(verificationDetails)` で行う．サーバーは `cnon:` で始まるトークンだけを受け付け，`CASH`／`EXTERNAL` や保存カードを使った支払済み偽装を拒否する．
- 購入受付と決済には固定の受付UUIDを使う．処理中・応答不明の場合は新しい請求を作らず，Squareの注文・決済を照合する．HTTPタイムアウトだけでは未払い扱いに戻さない．
- 決済直前に会員資格と在庫を読み直す．会員カート内の決済はD1のリースで直列化し，結果不明の購入分は解決まで保守的に差し引く．支払完了後も，注文ID・商品・店舗・数量が一致するSquareの売却記録と，それを含む在庫集計時刻を確認するまで確保を継続する．Sandboxの実接続で確認した約4秒の反映遅延に対応する．一般ストア・POSとの原子的な最後の1点の引当はSquare APIで保証できない．競合は運営確認対象にする．単品と5袋セットの既存SKU間の自動組み替えは行わない．
- 支払いを確認した注文はResendで注文受付メールを送る．配送先はSquareの注文で確認し，クリックポストを実際に引き渡した後，「運営画面 → ショップの注文・発送・在庫 → 注文と発送メール」でお問い合わせ番号を登録する．購入者へ追跡番号と日本郵便の追跡ページを案内する．送信状況は同じ画面で確認できる．Squareの発送操作でも購入者に通知されるため，APIショップの発送記録はHackSick側に統一する．
- Square OAuthトークンはD1で暗号化する．本番では専用アプリのOAuth接続だけを使い，既存HSAPアプリや本番の個人アクセストークンへフォールバックしない．
- 月額資格は `SQUARE_MONTHLY_PLAN_IDS` の明示されたプランだけを対象に，JPYの支払済み請求・関連注文・未返金の完了決済を照合する．日本時間の請求日とプランの請求基準日から対象期間を確定する．`ACTIVE` や `charged_through_date` 単独では付与しない．5分間隔の照合と購入直前の再確認を行う．
- `shop.hacksick.com` は独自ショップを表示する．発送・在庫・限定商品・クーポンの管理は `https://members.hacksick.com/operations` から運営アカウントで開く．

購入確認と運営への受付通知はResendのoutboxから送信する．配信直前に注文状態を再確認し，結果不明・在庫競合では購入者へ支払完了と断定したメールを送らない．Sandboxでは実メールを送信しない．

本番Webhookの宛先は `https://members.hacksick.com/api/square/webhook`．生本文と正確な通知URLのHMACを検証し，イベントIDを重複排除する．通知中のstatusを支払証明として扱わず，Squareの最新値を取り直す．

## 収益モデルと特典ルール

`src/business-policy.ts` に，2026年11月3日に共有された収益モデルのルール案を集約した．`status=draft` とし，本番のSquare Onlineの送料・販売価格・契約・クーポンは変更しない．Canvas本文は取得できなかったため，チャットへ貼付された内容を基準とする．

| 対象 | 実装した判定 |
| --- | --- |
| 通常購入 | 有効な会員・HSAP資格で商品代金10％引き |
| 定期便 | 通常商品価格とは別の定期便専用料金から会員はさらに5％引き．契約・月次処理は会員Workerで管理し，Square APIで決済する |
| クーポン | 会員割引と併用せず，対象商品に対する値引き額が最大の1つを使う．同額なら会員枠を優先する |
| 送料無料 | 税込・送料別の商品代金が，割引前で4,000円以上なら無料．それ未満は500円 |
| お試しセット | 仮案の3袋セット．商品代金は割引後も1セット980円を下回らない．本番SKUは作成しない |
| LT免除 | 日本時間の開催月について，同じ人はHSAPと月額会員を横断して1回まで |
| HSAP免除分 | 1回1,000円の内部配賦額を提供記録に保存．両資格がある人は月額会員枠を優先する |
| 入会ステッカー | 同じ人に初回1回．再入会で初回分を繰り返し発行しない |
| 継続ステッカー | 有効資格の連続した期間について6暦月ごと．資格の重複で継続月数を増やさず，中断後は再開時から数える |
| 登壇者特典 | ステッカーは同じ人・同じイベントにつき1回．珈琲は初登壇を運営が明示確認した人に1回だけ |

特典提供は `benefit_redemptions` に記録し，種類と期間またはイベントごとの一意制約で重複を防ぐ．LT免除は開催日時の資格を確認し，後日の退会によって過去の有効期間を消さない．同時登録でも同じ人の同月LT免除は1件に限定する．記録は在庫出庫・現物配送・会計ソフトへの仕訳を実行するものではない．

学生セット3,280円は提案値として保持し，販売は無効のままとする．HSAP会費と実サービス原価，ステッカー・近況報告書の原価，登壇者数，新規加入者への運営割の継続可否は未確定値として保持する．既存の運営会員を，新規向け価格や新ルールへ自動移行しない．

### 珈琲の定期便

契約と請求予定はHackSickのD1，カード保管・注文・決済・売却在庫はSquareのCards／Orders／Payments APIで管理する．Square Subscriptionsの契約を作成する方式ではなく，Squareのサブスクリプション一覧には珈琲定期便は表示されない．既存HSAP・月額会員の契約は読み取りだけで，作成・変更・解約を行わない．Square Onlineの有料プランは使わない．

`src/coffee-subscriptions.ts` に税別・送料別の基本料金，`src/coffee-recurring.ts` に申込・カード保存・請求・解約を実装する．`COFFEE_RECURRING_ENABLED=true`，既存決済の接続条件，ショップ専用OAuthの実許可スコープ `CUSTOMERS_WRITE` がそろったときだけ受付・月次決済を有効にする．単発購入の `CHECKOUT_ENABLED` とは別の停止スイッチである．ローカルの初期状態は両方とも無効．本番の現在の状態はROLLOUTを参照する．

| --- | ---: | ---: | ---: | ---: |
| 毎日HackSickプラン | 30 | 10,800円 | 11,664円 | 11,080円 |

#### 申込と月次運用

- 全プランとも，初回は3袋・税別980円，食品税78円＋送料500円で **1,558円** のお試し便を決済する．会員割引なし，決済後5日以内を目安に出荷する．月途中の袋数・金額の日割りはしない．
- 月末締め，翌月1日から毎月決済し，10日ごろ一斉発送する．月が替わってから初回決済を続けようとした申込は，初回通常便の日付を更新して再確認させる．
- Web Payments SDKで `CHARGE_AND_STORE` の本人認証を行い，支払済みのお試し便のPayment IDからSquareへカードを保存する．通常便の申込・カード保管・継続決済・解約条件への明示同意を保存する．初回支払が済んでカード登録だけ失敗したときは，お試しを再請求せず `STORE` でカード登録をやり直す．
- 専用アプリが作成した購入者用Square CustomerとCard参照を使う．既存HSAPの顧客・保存カードをメール検索で流用しない．カード番号・CVV・入力用nonceをD1に保存しない．参照ID・ブランド・下4桁・同意履歴を保持する．
- 日本時間1日のcronが，有効な同意・資格・共通在庫を確認してから保存カードで決済する．月ごとの一意制約，固定の注文・決済キー，共通の決済ロックで重複を防ぐ．Squareの売却記録が反映されるまでの保守的な確保も単発購入と共用する．
- 通常便は共通在庫から既存5袋セットを優先し，残りを単品で組み合わせる．在庫数の振替やSKU新設はしない．袋数分を確保できなければ請求を止める．今後の月の在庫予約・継続供給を保証する機能ではない．
- 結果不明は `review` とし，再請求せずSquareの現在の注文・決済を照合する．カード否承認や在庫不足は `action_required` に止め，自動で新しい請求を繰り返さない．同月分だけ本人が画面で再確認・再決済できる．過去月や1日全体の障害は運営が確認する．
- 本人は画面から今後の定期便を解約できる．請求処理と同じロックを取り，解約後の新規請求を止める．支払済みの注文の取消・返金はSquareで運営が確認する．Squareカードを自動無効化せず，既存HSAP等へ影響させない．
- 購入者への注文確認と，申込・解約・対応依頼のメールをoutboxへ保存し，Resendで配送する．運営宛には住所やカードIDを含めない．Sandboxでは外部へ送信しない．

### 一般ショップと会員ページの分離

`SHOP_BASE_URL` を設定すると，そのオリジンでは一般向けカタログと購入画面を表示する．`GET /api/storefront` はログインなしで商品と定期便の通常料金を返す．単発購入はゲストでも利用できる．会員価格・限定商品・クーポン・定期便にはメール確認が必要で，会員資格は割引判定に使う．会員ログインと購入のセッションCookieは各ホストに限定する．会員QR，LT受付，Square OAuth・Webhook，運営APIは従来どおり `AUTH_BASE_URL` 側で受ける．

一般ショップを公開するときは，書籍の返品条件と特商法表記をショップ内に掲載し，Workerの `SHOP_BASE_URL` と `shop.hacksick.com/*` のルートを設定する．302ルールを無効化し，公式サイトの書籍購入リンクも新ショップへ移す．Square商品ライブラリの同じSKUを参照するので，Square Online・POSと在庫は共通． `node scripts/test-square-sandbox.mjs --storefront` で珈琲2商品と書籍の通常価格決済・在庫減算を検証できる．
- `GET /api/admin/coffee`：運営の申込一覧．住所・カードIDは返さない．
- `POST /api/admin/coffee/reconcile`：注文・契約状態の照合だけを行う．新規請求はしない．

運営画面の「ショップの注文・発送・在庫」内に，定期便の申込一覧と照合ボタンを置く．お試し便と通常便も，発送後に「注文と発送メール」から通知できる．

#### 注文メールと定期便の例外対応

独自ショップと会員サイト経由の注文は，支払確定後に購入者へ受付番号・商品・支払額・出荷目安を送り，運営にも受付を通知する．実際にクリックポストへ引き渡した後，運営画面でお問い合わせ番号を登録すると，購入者に発送メールを送る．返信は `shop@hacksick.com` が受ける．Square Online経由の注文はSquare側で通知する．

運営画面の「配信サービス受付済み」はResendが送信依頼を受理した状態．到着しない場合や「送信要確認」の場合は同じ受付番号で注文・発送の記録とResendの配信履歴を照合する．通知の不達だけを理由に再注文・再請求・再発送はしない．必要な再案内は本人へ既存注文の内容を伝える．

| 起きたこと | 現行の処理 | 運営と購入者の対応 |
| --- | --- | --- |
| 月初の決済が完了 | 注文受付メールを送信し，翌月の請求日へ進む | 10日ごろの発送対象にし，引き渡し後に追跡番号を登録する |
| カードが否承認 | 自動請求を止め，状況確認メールを送る | 購入者が会員サイトで同じ月の支払いをやり直す．支払済みを確認して発送する |
| 応答が途切れ，支払い結果が不明 | 確認中としてSquareの決済を照合する | 照合中は再決済せず，発送を保留する．支払済みを確認できたら受付・発送へ，失敗が確定したら再支払いの案内へ進む |
| 在庫不足で請求を見合わせた | 請求を行わず確認待ちにする | 運営が補充と発送日を確認し，支払える状態になってから案内する |
| 決済後に在庫競合が判明 | 運営確認に移し，追加の請求は行わない | Squareで入金を確認して，納期変更か取消・返金を購入者と調整する |
| お試し便の決済後，カード保存だけ失敗 | お試し便は支払済みで，定期便はカード登録待ちになる | 支払済みのお試し便は通常どおり発送する．購入者はお試し代を払い直さず，次回用のカードを登録する |
| 解約・返金の相談 | 解約で今後の自動請求が停止する | 支払済みの便は受付番号と引き渡し状況を照合し，取消・返金はSquareで別途判断する |

現行の確認メールは，カード・在庫・決済結果不明で共通の文面を使用する．改善時は「カードを変更して再支払い」「処理中なので待つ」「補充を待つ」をそれぞれ案内し，送信直前に最新の状態を確認する．カードの再入力や再支払いを案内するのは未払いが確定した場合に限る．

発送締切の案は，日本時間7日23時59分までに支払確認できた通常便を10日ごろの発送に載せる運用．締切時点で入金結果が不明な注文は照合を続け，確定の連絡時に発送日を案内する．明示的な未払いは締切後に運営が確認し，当月を見送る場合は翌月再開の扱いとあわせて購入者へ案内する．現行の再支払いは同月中に可能で，締切・自動スキップ・翌月の自動再開は未実装．

本番初回の確認では，対象の注文1件について，支払確定後の受付メール，追跡番号付き発送メール，`shop@hacksick.com` への返信が届くことを確かめる．通知の重複・再試行は既存の自動テストで先に検証できる．

### 会員ショップの商品写真

Squareの商品ページと同じ暖色調の実物写真を，会員ショップの単品・5袋セットへ掲載する．表面写真は各商品カードへ，裏面ラベルは開閉式の案内へ置き，それぞれ原寸表示へリンクする．5袋セットの表紙には5袋を並べた写真を使い，両商品に淹れている様子を掲載する．未ログインでも表面写真と商品概要を確認できる．

元画像はGit管理外の `.imports/coffee-photos/`，配信するJPEGは `public/images/` に置く．写真情報は `src/product-media.ts` に分け，見積・決済の価格行や指紋に混ぜない．Square Onlineの有料顧客アカウント機能は使用しない．単発購入の送料は500円，送料無料条件は割引前5,000円以上のまま維持する．収益モデル案の4,000円へ自動変更しない．

### 採算の扱い

`src/commerce.ts` は，値引き後の商品代金と受取送料を売上とし，決済手数料，珈琲仕入の保守的な仮置き260円／袋，クリックポスト240円／梱包，梱包費，人件費，その他原価を見積もる．収まる梱包数は推測せず，試算時に指定する．未確定原価は `null` として `incomplete` を返し，利益を確定しない．判明分だけでもマイナスなら `loss` を返す．

`contributionJpy` は指定した実費と機会費用を引いた採算であり，会計上の最終利益とは区別する．`cashContributionJpy` は指定した実費のみを引いた金額．例えば，月額1,500円，決済手数料3.6％，LT免除を1回1,000円の機会費用とした月2回のケースでは，前者が−554円，後者は追加実費を入れる前で1,446円となる．免除額そのものを現金支出と断定しない．

内部配賦は団体全体の採算から二重控除せず，`internalAllocationJpy` として分ける．HSAPへ1,000円を配賦しても，HackSick全体の支出や機会費用は消えない．学生セットの「482円残る」という値も，HSAPの実原価等が確定するまで保証しない．

決済手数料は試算ごとに指定する．注文プレビューの初期値3.6％は[SquareのeコマースAPI決済](https://squareup.com/jp/ja/payments/our-fees)向けであり，月額会費の請求方式にも同じ料率を適用する前提にはしない．手数料の円未満は四捨五入した概算とし，実際のSquare精算額を優先する．クリックポストは[日本郵便の2026年10月改定](https://clickpost.jp/)の240円を使用する．

### LT・協力者クーポンの条件案

2026年11月7日の追加要望により，LT参加者向けは商品代金10％引き・発行から30日間，撮影・イベント協力者向けは別コード・別率を想定する．原価の最新の説明は「定価400円の60％」であるため，以前の180円を採算の初期値として使わない．`src/coffee-cost-policy.ts` へ基準240円を保存し，仕入れ時の税込・税別が未確認のため，8％込みを切り上げた260円／袋を保守的に仮置きする．仕入送料，梱包，作業，その他原価は含まない．この変更は販売価格や契約の請求額を変更しない．

`src/promotion-policy.ts` に，LT10％，イベント協力者20％・上限400円の従来案と，撮影協力者50％を分けて置いた．撮影協力者向けは，撮影1枚あたり3,000円を割引枠とする試算で，5枚なら15,000円．税込の商品代金の50％と割引枠のうち小さい額を値引きする．購入が数回に分かれる場合は実際の値引き額を残高から引く想定であり，期限と利用回数は未確定．LT・イベント協力者用の案は有効期間30日・1アカウント1回とする．

いずれも単発購入に適用し，値引きの計算には対象商品の代金を使う．試算APIは会員割引とクーポンのうち値引き額が大きい方を選び，同額なら会員枠を優先する．実際の発行時は，ショップ運営画面で併用の可否を設定できる．

クーポン案の試算は現在の送料500円・割引前税込5,000円以上無料という条件で計算し，収益モデル案の4,000円を使わない．`POST /api/admin/simulations/coupon` は `kind=lt|supporter|photographer`，通常商品の `items`，任意の `memberId`，`parcels`，注文全体の `packagingJpy`・`laborJpy`・`otherCostsJpy`，`feeBasisPoints` を受け付ける．`photographer` の場合は `photoCount` で試算用の撮影枚数を指定できる（省略時1枚）．料金・会員資格・割引率・1枚あたりの割引枠はサーバーが確定する．手数料予算は切り上げ，未確定の配送・梱包・作業・その他原価を0円扱いせず，結果を未確定にする．この判定は与えた仮定の範囲に限り，実際の黒字を保証しない．

撮影協力者用の採算は，購入元から直送し，HackSickへの仕入請求が税込150円／袋になる条件を別途想定して検討した．5袋セット1個を50％引きすると商品代金1,026円・送料500円．直送関連費500円と決済手数料3.6％を含めると約221円が残る．この150円は通常仕入れの原価設定に適用せず，試算APIは従来どおり260円／袋を使う．実際の発行前に直送時の請求単価と発送費を確認する．

### 管理API

- `GET /api/admin/policy`：ルール案と未確定項目を確認する．
- `GET /api/admin/members/:id/benefits`：現在月の免除可否，未提供ステッカー特典，提供履歴を確認する．
- `POST /api/admin/members/:id/benefit-redemptions`：`kind`，確認理由 `reason` を指定して提供記録を作る．イベント特典は `eventId` とタイムゾーン付き `eventAt`，登壇者特典は `speakerConfirmed=true`，初登壇の珈琲は加えて `firstTalkConfirmed=true` が必要．
- `POST /api/admin/simulations/order`：`items=[{sku,quantity}]`，任意の `memberId`，試算用 `couponPercent` と原価を指定する．商品価格と会員資格はサーバーが確定し，入力された価格や資格フラグは採用しない．このAPIは通常商品だけを扱うため `recurring=true` を拒否し，通常価格を定期便の基本料金として代用しない．`parcels`，`packagingJpy`，`laborJpy`，`otherCostsJpy` が未指定なら未確定扱い．`feeBasisPoints=360` は3.6％．

全APIで運営権限が必要．POSTは変更担当者のみ．試算は `live=false`，`stockReserved=false` を返し，決済・在庫引当・クーポンの実発行は行わない．提供記録の保存と同時に確認者・理由・配賦額を監査履歴へ保存する．
